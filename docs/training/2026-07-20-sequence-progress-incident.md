## Корневая причина

Метод `getModuleCompletionGateStats()` ошибочно считал блокирующей любую активность, когда выполнялось хотя бы одно условие:

```php
$isBlocking = !empty($activity['is_required'])
    || !empty($activity['block_next_module_until_passed']);
```

Для перехода между модулями необходимо учитывать только:

```php
!empty($activity['block_next_module_until_passed'])
```

При этом обязательная активность с `is_required=1`, но `block_next=0` продолжает учитываться в полном завершении модуля, однако не закрывает следующий модуль.

Дополнительно `recalculateUserCourse()` выбирал текущий модуль по сводному полю `TrainingUserModuleProgress.completed`. Из-за незавершённой, но неблокирующей практики модуль 0 оставался текущим. Текущий навигационный модуль должен определяться по первому незавершённому **navigation gate**.

## Правильная логика после исправления

1. Полное завершение модуля может учитывать все обязательные активности.
2. Переход к следующему модулю блокируют только активности с `block_next_module_until_passed=1`.
3. Модуль 0 имеет navigation gate `1/1`, поэтому не блокирует модуль 1.
4. Модуль 1 имеет navigation gate `6/7`, поэтому доступен сам, но блокирует модуль 2.
5. Текущий модуль определяется по первому незавершённому navigation gate.
6. Сырые данные прогресса, тестов и практик при исправлении не изменяются.

## Обязательный порядок дальнейших работ

Git нельзя считать безусловно актуальным относительно production.

Перед любой новой правкой Training:

1. Провести короткую read-only диагностику фактических файлов, SHA методов, таблиц, флагов и данных на сервере.
2. Не выполнять массовые пересчёты и не обходить всех пользователей без доказанной необходимости.
3. Не использовать жёстко заданные имена таблиц — разрешать реальные таблицы динамически.
4. Если код на сервере отличается от Git, сначала получить фактические методы/файл и только затем готовить изменение.
5. Перед применением создать отдельный бэкап файла и затрагиваемых строк БД.
6. Apply-скрипт обязан проверять SHA или структуру фактического исходного кода и останавливаться до записи при несовпадении.
7. После применения выполнить точечную проверку на тестовом пользователе.
8. Только после подтверждения на сайте синхронизировать точные изменённые файлы в Git.
9. Не использовать `git reset`, `git checkout`, `git clean`, `git pull`, `git merge`, `git rebase`, `git add .` и `git add -A` на рабочей грязной копии.
10. В Git добавлять только точные проверенные пути. Бэкапы, диагностики, дампы, медиа и временные файлы не коммитить.

## Формат MODX Console

- каждый PHP-файл начинается с `<?php`;
- сначала read-only диагностика;
- затем отдельный apply с бэкапом;
- затем отдельный rollback;
- вывод — читаемые строки, без Unicode escape и без громоздкого вложенного JSON;
- прямые `.php`-файлы, без архивов.
