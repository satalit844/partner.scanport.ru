## Главный рабочий принцип

Нельзя считать Git безусловно актуальным относительно production.

Перед любой новой правкой обязательна короткая точечная read-only диагностика фактического состояния на сервере. Особенно это обязательно, когда:

- данных не хватает;
- файл или метод отсутствует в предоставленном контексте;
- версия в Git может быть старее production;
- таблица, поле, класс или путь не подтверждены;
- предыдущие изменения могли выполняться через MODX Console;
- задача затрагивает прогресс, тесты, практики, доступы или последовательность обучения.

Если Git устарел, сначала диагностируем фактический серверный файл, методы и SHA. После успешного тестирования синхронизируем только точные изменённые пути в рабочую ветку.

## Обязательный порядок работы

### 1. Диагностика

Сначала подготовить отдельный read-only PHP-файл для MODX Console.

Диагностика должна:

- начинаться с `<?php`;
- ничего не менять в БД и файлах;
- не очищать кэш;
- не выполнять массовый пересчёт;
- не обходить всех пользователей без необходимости;
- проверять только нужный курс, пользователя, модуль, активность или файл;
- определять реальные таблицы и поля динамически;
- выводить фактические пути, ID, флаги, статусы, SHA и используемые методы;
- при работе с PHP-методами извлекать их через `token_get_all()`, а не искать по хрупкому совпадению текста;
- выдавать читаемые строки, а не вложенный JSON с Unicode escape.

Финал диагностики:

```text
RESULT=SUCCESS
NO_CHANGES_MADE=YES
NEXT=...
```

После запуска пользователь присылает полный результат. До анализа результата apply-файл не готовить.

### 2. Анализ результата

Нужно явно установить:

- корневую причину;
- какие данные являются исходными;
- какие строки и файлы затрагивать нельзя;
- что именно должно измениться;
- какие проверки доказывают правильность решения.

Не делать выводы только по скриншоту, агрегированному проценту или одному полю, когда есть сырые таблицы прогресса.

### 3. Применение

Только после диагностики подготовить отдельный apply PHP-файл.

Apply обязан:

- начинаться с `<?php`;
- создать отдельный бэкап каждого изменяемого файла и затрагиваемых строк БД;
- проверять фактический исходный SHA метода или структуру файла;
- останавливаться до записи при несовпадении;
- заменять методы через PHP tokenizer, если нужно менять метод целиком;
- не использовать хрупкий `str_replace()` большого текстового блока;
- не использовать жёсткие имена таблиц без подтверждения;
- применять только минимальное точечное изменение;
- очищать кэш и OPcache только после успешной записи;
- выводить, что именно изменено и что не изменялось.

Финал apply:

```text
RESULT=SUCCESS
BACKUP=...
ERRORS=0
NEXT=...
```

### 4. Откат

Одновременно с apply подготовить отдельный rollback PHP-файл.

Rollback должен восстанавливать только изменение этого apply-файла из созданного им бэкапа.

### 5. Проверка

После применения сначала проверяется один конкретный тестовый пользователь и ожидаемое состояние интерфейса. Нельзя сразу запускать массовую миграцию или пересчёт всех пользователей.

После подтверждения пользователя можно выполнять точечную финальную синхронизацию и фиксировать результат в Git.

## Формат файлов

- Давать прямые `.php`-файлы для скачивания, не архивы.
- Каждый PHP-файл всегда начинается с `<?php`.
- Имена файлов версионировать: `_diagnostic_v1`, `_apply_v1`, `_rollback_v1`.
- Вывод делать коротким и читаемым.
- Код и команды давать в копируемых блоках.

## Ограничения по данным

Без прямого доказательства запрещено:

- ставить пользователям `completed=1`;
- создавать фиктивные попытки тестов или практик;
- отмечать практику одобренной;
- восстанавливать прогресс по предположению;
- массово пересчитывать все курсы;
- удалять или обнулять строки прогресса;
- менять несколько курсов, если задача касается одного;
- использовать один тестовый результат как основание для массовой правки.

## Git-безопасность

Рабочая копия может содержать посторонние изменения и бэкапы.

Запрещены широкие команды:

```text
git reset
git checkout
git clean
git pull
git merge
git rebase
git restore .
git add .
git add -A
```

Разрешён только точечный процесс:

```text
git status --short
git diff -- точный/путь
git add -- точный/путь
git diff --cached -- точный/путь
git commit -m "..."
git push origin sync/server-working-20260627
```

Не коммитить:

- серверные бэкапы;
- дампы БД;
- временные диагностические результаты;
- `.ai_context`;
- большие медиа;
- случайные локальные удаления;
- файлы вне точного списка задачи.
